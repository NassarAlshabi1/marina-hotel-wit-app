# دليل تحديث قاعدة البيانات والتكامل مع وحدة Smart Auto-Fix

هذا المستند يضع خارطة الطريق التفصيلية لتحديث مخطط قاعدة بيانات Drift ودعم وحدة **Smart Sync + Smart Restore + Auto-Fix** داخل تطبيق الفندق. يوضح التغييرات المطلوبة على الجداول، خطوات الترحيل، وآلية التكامل مع منطق الإصلاح التلقائي بعد الاستعادة.

---

## 1. الأهداف الرئيسية

- توفير حقول متوافقة مع متطلبات المزامنة ثنائية الاتجاه (UUID، طوابع زمنية بصيغة ISO).
- تمكين حساب الليالي والمبالغ تلقائيًا بعد استعادة نسخة احتياطية، مع احترام دورة اليوم الفندقي (14:00).
- دعم إعادة حساب المدفوعات، حالات الغرف، المصاريف، الديون، والرواتب دون خسارة بيانات.
- تجهيز قاعدة البيانات لعمليات الدلتا السريعة والمنعزلة (batch inserts/updates + مؤشرات محسّنة).
- حفظ سجلات تدقيق شاملة لكل عملية إصلاح واستعادة.

---

## 2. التغييرات على المخطط (Schema Changes)

### 2.1 حقول المزامنة الموحدة
- تحديث mixin `SyncFields` لتحويل الحقول الزمنية إلى صيغة ISO:
  - `createdAtIso`, `updatedAtIso`, `deletedAtIso (nullable)`.
  - الاحتفاظ بحقلي Epoch (`createdAtEpoch`, `lastModifiedEpoch`) لخدمة الفهارس ومقارنة الدلتا.
- تحديث جميع الجداول المعتمدة على `SyncFields` لتحويل القيم الحالية من أرقام إلى نصوص ISO أثناء الترحيل.

### 2.2 جدول الليالي (BookingNights)
- إنشاء جدول جديد يحفظ تفاصيل كل ليلة مع المفتاح الفندقي:
  - `bookingLocalId`, `hotelDayKey`, `nightStart`, `nightEnd`, `nightlyRate`, `sequence`.
  - قيد أساسي مركب `{bookingLocalId, hotelDayKey}` لضمان idempotence.
  - فهارس على `(hotelDayKey)` و`(localUuid)`.

### 2.3 تحديث جدول الحجوزات (Bookings)
- إضافة أعمدة مشتقات وحالة مالية:
  - `stayDurationIso`, `totalNightsCached`, `lastNightEpoch`.
  - `isOverdue`, `needsCheckoutReview`.
  - `totalDueCached`, `totalPaidCached`, `remainingBalanceCached`, `isFullyPaid`.
  - مفاتيح دورة اليوم: `hotelDayCheckin`, `hotelDayCheckout`.
  - `guestUuid` للربط بجدول النزلاء.
- فهرس مركب على `(status, hotelDayCheckout)` لتسريع إيجاد الحجوزات النشطة بعد الاستعادة.

### 2.4 جداول إضافية
- **Guests**: تعريف الضيوف ومؤشرات الزيارات (`guestUuid`, `fullName`, `totalVisits`, `lastVisitHotelDay`).
- **Services** / **Settings**: لتخزين الخدمات والإعدادات المتزامنة عبر الأجهزة.
- **SalaryCycles** و **SalaryPayments**: لتتبع الرواتب والدفع الجزئي.
- **PendingBalances** أو توسيع Debts لحفظ الأرصدة المعلّقة الناتجة عن Auto-Fix.
- **HotelDayLedger** (اختياري لكن موصى به): لتجميع الإيرادات/المصروفات لكل يوم فندقي.
- **BackupManifest**, **AutoFixRuns**, **IntegrityViolations**: سجلات تدقيق وتحليل صحة البيانات.

### 2.5 تحديثات الجداول الحالية
- **Rooms**: إضافة `cleaningStatus`, `lastCleanedHotelDay`, `lastOccupiedHotelDay`, `requiresMaintenance`.
- **Payments**: إضافة `hotelDayKey`, `isPendingBalance`, `linkedDebtUuid`, `bookingUuidCache` مع فهارس مناسبة.
- **Expenses**: إضافة `hotelDayKey`, `categoryUuid`, `cashFlowUuid`, `isAutoGenerated`.
- **Debts**: إضافة `debtUuid`, `hotelDayOpened`, `hotelDayClosed`, `isFromAutoFix`.
- **SyncQueue / SyncLog / SyncConflicts**: إضافة فهارس على الحقول الزمنية بصيغة ISO.
- ضمان وجود فهرس على `localUuid` في كل جدول مزامنة.

## 3. خطة الترحيل (Migration Plan)

1. **رفع نسخة احتياطية** قبل أي تعديل (Script أو أداة موجودة).
2. **إضافة الأعمدة الجديدة** مع قيم افتراضية تلائم البيانات الحالية:
   - الأعمدة النصية تأخذ القيم الحالية بعد تحويلها (مثال: `datetime.fromMillisecondsSinceEpoch` → `toUtc().toIso8601String()`).
   - القيم المشتقة (totalPaidCached) تترك مبدئيًا بـ 0 أو null ويتم تحديثها في مرحلة إعادة البناء.
3. **تحويل البيانات الزمنية** لجميع الجداول:
   - تحديث `createdAt`, `updatedAt`, `deletedAt` إلى الأعمدة الجديدة مع الحفاظ على النسخة الرقمية.
4. **إنشاء الجداول الجديدة** (`booking_nights`, `guests`, `salary_cycles`, ... إلخ).
5. **ملء الجداول المشتقة**:
   - إنشاء سجلات BookingNights عبر دالة تستخدم قاعدة الساعة 14:00.
   - تحديث `totalNightsCached`, `totalPaidCached`, `remainingBalanceCached` حسب البيانات الحالية.
   - إسناد `hotelDayKey` لكل صف (Bookings, Payments, Expenses) وفق دالة `HotelDay.fromDate`.
6. **تكوين الفهارس** بعد استكمال إدخال البيانات لتجنب بطء الإدراج.
7. **تحديث DAOs والمعالجات** لقراءة/كتابة الحقول الجديدة.
8. **تشغيل اختبارات التأكد** (unit/integration) للتأكد من نجاح الترحيل.
9. **إزالة الأعمدة القديمة** (إن وجدت) بعد التأكد من عدم استخدامها في الكود.

> **ملاحظة:** يُنصح بتنفيذ الترحيل على بيئة تطوير أو نسخة staging قبل البيئة الفعلية. ستحتاج التحويلات إلى حماية عبر معاملات (`transaction`) لتجنب حالات نصف منتهية.

## 4. تكامل Auto-Fix مع البنية الجديدة

### 4.1 تدفق Restore + Auto-Fix
1. `restoreFromBackup()` يستدعي:
   - التحقق من صلاحية النسخة (schemaVersion، عدد الصفوف، العلاقات).
   - تطبيق snapshot على قاعدة البيانات (`applyMergedData`).
2. بعد اكتمال الاستعادة:
   - تشغيل `PostRestoreAutoFixService` داخل isolate أو task مخصص.
   - الخطوات الفرعية:
     1. **إعادة بناء BookingNights** (باستخدام الجداول الجديدة).
     2. **حساب القيم المالية** للحجوزات (`totalDue`, `totalPaid`, `remaining`).
     3. **إصلاح المدفوعات اليتيمة** عبر مطابقة `localUuid`/`bookingUuidCache`.
     4. **تعديل حالة الغرف** اعتمادًا على حجوزات اليوم.
     5. **تحديث المصاريف/الديون/الرواتب** حسب اليوم الفندقي.
     6. **تجديد الحقول المشتقة** (cache fields + hotelDay ledger).
3. تسجيل نتائج الإصلاح في:
   - `AutoFixRuns` (ملخص تنفيذي).
   - `RestoreFixLog` و`IntegrityViolations` للعمليات الفردية.
4. تعقب الزمن (`executedAt`, `durationMs`) والتقارير لتسهيل المزامنة مع الأجهزة الأخرى.

### 4.2 ضمان Idempotence
- الاعتماد على القيود المركبة (Primary key) في `BookingNights`, `PendingBalances`.
- تخزين علامة `generatedByAutoFix` لتجنب التكرار عند إعادة التشغيل.
- استخدام معاملات مع Safe Savepoints لكل مجموعة حجوزات.

### 4.3 تحديث طبقة السينك
- `DeltaSyncService` يقرأ الحقول الجديدة (خصوصًا `updatedAtIso`).
- التأكد من أن الضخ للـ delta يستخدم hash يتضمن الأعمدة المشتقة لمنع تجاهل التغييرات.
- بعد Auto-Fix، يتم استدعاء `syncAllTables(force: true)` لإرسال التعديلات للأجهزة الأخرى فورًا.

## 6. الاختبارات المطلوبة

- **اختبارات وحدة Auto-Fix:**
  - استعادة بيانات قديمة لحجز نشط والتأكد من إعادة بناء الليالي والمدفوعات.
  - سيناريو مدفوعات ناقصة/زائدة والتحقق من إنشاء `pending balance` أو وضع `overpaid`.
- **اختبارات تكامل Restore:**
  - استعادة كاملة مع بيانات متعددة (حجوزات، مصاريف، ديون، رواتب).
  - التأكد من أن الحقول المشتقة تمت إعادة حسابها.
- **اختبارات Delta Sync:**
  - تشغيل `compute()` بعد Auto-Fix والتأكد من إرسال التغييرات الصحيحة.
- **اختبارات الأداء:**
  - قياس زمن تشغيل Auto-Fix على بيانات كبيرة، ضمان البقاء ضمن حدود زمنية معقولة بفضل batching والمعاملات.

## 9. ملاحق

- **توليد hotelDayKey:**
  ```dart
  class HotelDay {
    final DateTime start;
    final DateTime end;
    final String key;

    HotelDay._(this.start, this.end, this.key);

    static HotelDay fromDate(DateTime date) {
      final normalized = date.toUtc();
      final cutOffHour = 14;
      final startCandidate = DateTime.utc(normalized.year, normalized.month, normalized.day, cutOffHour);
      final start = normalized.isBefore(startCandidate)
          ? startCandidate.subtract(const Duration(days: 1))
          : startCandidate;
      final end = start.add(const Duration(days: 1));
      final key = '${start.year}-${start.month.toString().padLeft(2, '0')}-${start.day.toString().padLeft(2, '0')}';
      return HotelDay._(start, end, key);
    }
  }
  ```
- **ملاحظة حول التحويل من Epoch إلى ISO:**
  ```sql
  UPDATE bookings
  SET created_at_iso = datetime(created_at_epoch / 1000, 'unixepoch'),
      updated_at_iso = datetime(updated_at_epoch / 1000, 'unixepoch'),
      deleted_at_iso = CASE WHEN deleted_at_epoch IS NULL OR deleted_at_epoch = 0
                            THEN NULL
                            ELSE datetime(deleted_at_epoch / 1000, 'unixepoch')
                       END;
  ```
