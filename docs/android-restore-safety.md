# سلامة النسخ والاستعادة — الدفعة الثالثة

تاريخ العمل: 2026-10-04. الإصدار البرمجي: `73940db6d6719dd57bdba82c345961838c8cb75a`.

## تغيير وظيفي مهم: استعادة SQLite موقوفة مؤقتًا

المسار السابق كان ينسخ ملف النسخة فوق ملف قاعدة البيانات الحية بينما اتصالات Room مفتوحة، ثم يحذف WAL/SHM. هذا ليس استبدالًا آمنًا لقاعدة مفتوحة وقد يعرّض البيانات للتلف.

- أزيل الاستبدال المباشر، وأصبح طلب استعادة `.sqlite/.db` يُرفض برسالة واضحة **قبل لمس الملف المصدر أو القاعدة الحية**.
- النسخ القديمة لا تُحذف، ولا تُحوّل صيغتها تلقائيًا.
- زر إنشاء نسخة في `BackupViewModel` أصبح ينشئ JSON مضغوطًا `.json.gz` بدل SQLite، لكي يظل إنشاء نسخة بصيغة قابلة للاستعادة متاحًا.
- JSON هو تنسيق البيانات الموجود أصلًا في التطبيق، وليس بديلًا مطابقًا لكل محتويات ملف SQLite: نطاقه `BACKUP_TABLE_KEYS` مع القائمة السوداء وحالة المزامنة؛ لا يشمل بالضرورة الجلسات وطوابير المزامنة والجداول الداخلية كلها.
- إعادة تفعيل استعادة SQLite تحتاج مسارًا مستقلًا: التحقق من الملف/المخطط، إيقاف مالكي الاتصال والمزامنة، واستعادة مرحلية مع استرجاع آمن عند الفشل. **هذا المسار لم يُنفَّذ بعد**.

## إصلاح المعاملات ومعالجة الفشل

### إنشاء واستيراد JSON

- تُقرأ جداول النسخة الجديدة داخل معاملة Room واحدة، ثم يُضغط الملف خارج المعاملة، لتجنب جمع جداول من لحظات مختلفة أثناء وجود كتابات متزامنة.
- الاستيراد داخل `Room.withTransaction`، مع نقاط تحقق من إلغاء coroutine قبل الكتابة وبين الصفوف وقبل إنهاء المعاملة.
- الجدول الموجود في JSON يجب أن يكون قائمة؛ كل صف يجب أن يكون خريطة غير فارغة. لم يعد الصف التالف يُتجاهل بعد حذف الجدول القديم.
- فشل جدول متأخر يتراجع عن تعديلات الجداول السابقة داخل معاملة الاستيراد. الجداول الغائبة ما زالت تُترك كما كانت، حفاظًا على عقد الملفات الجزئية السابق.
- بقيت معالجة JSON/GZIP وأسماء الأعمدة والصيغ السابقة؛ لم يُضف تحويل جديد لقيم الحسابات المالية.

### الإصلاح اللاحق للاستعادة

- إصلاح الحجوزات والحسابات وحالات الغرف وسجلات التفاصيل وسجل النجاح أصبح معاملة واحدة.
- عند فشل SQLite، تُلغى تعديلات المعاملة أولًا، ثم يُحاول تسجيل تشغيل فاشل خارجها، مع عدادات إصلاح صفرية بدل عدّ تغييرات تم التراجع عنها.
- فشل كتابة سجل الفشل لا يستبدل السبب الأصلي: يحتوي التقرير على الخطأين.
- إلغاء coroutine لا يُحوَّل إلى تقرير فشل عادي. الأخطاء غير المتوقعة تنتقل إلى المستدعي بعد تراجع المعاملة.
- لم تتغير استعلامات حساب المبالغ أو قواعد الخصومات والليالي. الاختبار يثبت العقد الحالي: الوصول إلى 14:01 بالضبط في اليوم الثالث يحتسب الليلة الثالثة.

### نتيجة الواجهة

- أصبح `BackupViewModel` يفحص `RestoreFixReport.requireSuccess()` قبل نشر حالة النجاح أو snackbar الأخضر.
- إذا اكتمل استيراد البيانات ثم فشل الإصلاح، توضّح الرسالة أن بيانات النسخة حُمّلت لكن الإصلاح اللاحق فشل.
- لم تعد معالجات الأخطاء العامة في هذا ViewModel تبتلع `CancellationException`.

**حد مهم:** الاستيراد والإصلاح اللاحق معاملتان منفصلتان، وليسا عملية واحدة قابلة للتراجع بالكامل. إذا نجح الاستيراد وفشل الإصلاح، تبقى البيانات المستوردة؛ الذي يُلغى هو تعديلات الإصلاح. لا يدّعي هذا التغيير استعادة شاملة ذرية من البداية للنهاية.

## الاختبارات

أضيف 13 اختبارًا: 11 اختبار Room/ViewModel على API 34 واثنان لعقد تقرير الإصلاح. التغطية تشمل:

1. تثبيت الإصلاح وسجلي التفاصيل والتشغيل معًا عند النجاح.
2. فشل تحديث الغرف بعد تعديل الحجز: رجوع صفوف الحجز والغرفة والسجل التفصيلي.
3. فشل تسجيل النجاح: رجوع الإصلاح كله.
4. فشل الإصلاح وفشل سجل الفشل معًا: الاحتفاظ بالسببين.
5. إلغاء فعلي بعد بدء الكتابة: رجوع الصفوف وعدم إنشاء سجل نجاح/فشل عادي.
6. رفض استبدال SQLite الحي دون تغيير المصدر أو الصفوف.
7. إنشاء JSON مضغوط بواسطة الخدمة ثم استعادته عبر واجهتها العامة.
8. استعادة JSON وGZIP الصحيحين مع بقاء الجداول غير المذكورة دون تغيير.
9. رفض الصفوف/أنواع الجداول التالفة، بما فيها فشل جدول متأخر بعد حذف جدول سابق.
10. إلغاء استيراد JSON بعد بدء الحذف وإثبات التراجع عنه.
11. اختبار ViewModel حقيقي مع Room: الإصلاح الفاشل لا ينتج رسالة نجاح.
12–13. عقد منع النجاح عند تقرير فاشل والسماح به عند تقرير ناجح.

اختبارات البيانات تستخدم قاعدة ذاكرة وبيانات اصطناعية، دون اتصال ببيانات الفندق. أضيف أيضًا تلخيص محدود لأخطاء JUnit في CI لأن رابط artifact قد لا يكون قابلًا للتنزيل من بيئة الوكيل؛ فُحص اكتشاف XML وتهريب محارف annotations محليًا.

## حدود العمل والمتابعة

- لا توجد شهادة بأن جميع مسارات النسخ أو الحسابات خالية من العيوب؛ التحقق الحالي من بنية صفوف JSON ليس تحققًا كاملًا من المخطط أو بصمة النسخة أو سلامة جميع العلاقات.
- لم تُبنَ استعادة SQLite الآمنة بعد، ولم يُختبر مسار استعادة إنتاجي ببيانات حقيقية.
- لم يُضف وضع صيانة لإيقاف المزامنة أثناء الاستعادة أو تسوية outbox مع بيانات النسخة؛ التوافق بين الاستعادة المحلية وحالة السحابة يحتاج عملًا واختبارات مستقلة. لم تُختبر أحجام نسخ كبيرة أو حدود الذاكرة في هذه الدفعة.
- المحاكي يفحص الدخول والإقلاع المعزول، وليس تدفق واجهة كاملًا للاستعادة على هاتف فعلي.
- لم تُعد ميزة عكس القيود أو إقفال الفترات الملغاة سابقًا، ولم تُعطّل قواعد الجودة لإخفاء الملاحظات.
