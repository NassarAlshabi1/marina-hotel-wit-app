**فصل مهم:** المحاكي ليس مقياس سرعة الهاتف. توضح وثائق Android أن Macrobenchmark يحذّر من القياس على المحاكي لأن النتائج تتأثر بموارد الحاسوب المضيف، وتوصي بجهاز حقيقي. ولا يعطي Lint أو Detekt وحدهما نسبة «جودة التطبيق» أو ضماناً لصحة الحسابات.

## ما أضيف عملياً

### GitHub Actions

المسار `.github/workflows/android-quality-and-emulator.yml` يعمل عند الدفع على فرع الجلسة، ويمكن تشغيله يدوياً حيث تسمح صلاحيات GitHub:

1. **quality**: يشغل `:app:lintDebug :app:detekt --continue`. ظهور مشاكل يجعل المهمة تفشل؛ لا baseline مولّداً لإخفاء المشكلات ولا ignoreFailures. الاستثناء المحدد الوحيد: تسمية دوال Compose بحروف كبيرة وفق عرف Compose.
2. يحفظ تقارير الأدوات و`quality-evidence/summary.json`. القيمة `null/report_not_generated` تعني أن الأداة لم تنتج تقريراً، **وليست صفراً من المشكلات**.
3. **emulator**: يبني Debug، ويشغّل Android 34 / Pixel 5، ويجمع خمس محاولات إقلاع، لقطات شاشة، frame stats، الذاكرة، سجل التعطل وشجرة عناصر الواجهة.
4. يحتفظ بالأدلة 14 يوماً في artifacts باسم `android-code-quality` و`android-emulator-evidence`.

اختيار Debug هنا لتشخيص الوظائف والشاشات، لا لإعلان سرعة release. أزمنة `am start -W` تشخيصية وليست Macrobenchmark TTID/TTFD. لا حد أداء مضللاً، ولا اختبار golden أو مقارنة صور تلقائية مضافة حتى الآن.

### السلامة والتغطية الفعلية

- سكربت المحاكي يرفض الهاتف الفعلي، ويستخدم تثبيتاً جديداً على محاكي مؤقت.
- يُحجب خروج الشبكة IPv4 وIPv6 لعملية التطبيق قبل أول إطلاق. إن لم تنجح قواعد الحجب يتوقف الاختبار. السبب أن التطبيق يبدأ محرك المزامنة تلقائياً، ولا ينبغي لاختبارات CI الوصول إلى بيانات الفندق.
- لا تُدخل حسابات الإنتاج في Maestro أو CI، ولا ترفع صور جهاز يحتوي على بيانات ضيوف.
- مسار CI الحالي يفحص **شاشة الدخول/الإقلاع على قاعدة جديدة**. لا يدّعي قياس Dashboard أو معالجة المدفوعات دون حساب وبيانات اختبار محلية.
- تدفق Maestro المضاف **غير مشغّل آلياً في CI**. تشغيله محلياً بعد إعداد محاكي معزول وتسجيل دخول بحساب اصطناعي:

```bash
mkdir -p performance-evidence
maestro test --format junit --output performance-evidence/maestro.xml .maestro/dashboard-sync-health.yaml
```

- اختبار معالجة المدفوعات تحت حمل يحتاج بيانات حجوزات ومدفوعات اصطناعية قابلة لإعادة الإنشاء، ثم Macrobenchmark على release وجهاز فعلي. لم نزوّر هذه البيانات أو ندّع نتائج لهذه الخطوة.
- لم يُستخدم اختبار Patrol القديم الموجود في androidTest على أنه اختبار Compose صالح؛ تكامله منفصل ويحتاج مراجعة قبل تشغيل connectedAndroidTest.

## شاشة «حالة المزامنة»

المسار في التطبيق: **الإعدادات → حالة المزامنة**، route: `sync_health`.

المرجع المقروء: `feat/cloudflare-sync-execution@78c17381`:
- `mobile/lib/screens/settings/sync_health/sync_health_screen.dart`
- `mobile/lib/services/sync_health_monitor.dart`

### ما تعرضه

- حالة المحرك الحية ورسالة المرحلة؛ مؤشر غير محدد أثناء التشغيل.
- تفعيل المزامنة وآخر رفع/سحب ناجحين محفوظين فعلياً.
- الحالة العامة: سليم محلياً، انتظار، تحذير، خطأ أو حرج.
- Outbox: المعلق، قيد المعالجة، الفاشل، المسلّم المحتفظ به، العالق لأكثر من 5 دقائق وعمر أقدم تغيير غير مسلّم.
- توزيع التغييرات غير المسلّمة حسب الكيان.
- أعداد سجلات الجداول الرئيسية، وليست أحجام التخزين بالبايت.
- عدد مخالفات `PRAGMA foreign_key_check`.
- روابط إلى سجل أخطاء المزامنة وإعداداتها.

### دقة البيانات والأداء

- قراءة مجمعة فقط على Dispatchers.IO داخل snapshot متسق، دون تحميل payloads أو تشغيل إصلاحات/حذف/رفع/سحب.
- تحديث عند الدخول وكل 30 ثانية أثناء ظهور الشاشة، مع زر تحديث يدوي ومنع تداخل طلبات التقرير. يتوقف مؤقت التحديث في الخلفية.
- يعتمد التصنيف على acknowledgement أولاً، ويأخذ primary_processing_status وprocessing_status معاً حتى لا تختفي الإخفاقات بسبب اختلاف الحقول.
- النطاق: صفوف Outbox المحلية فقط. «مكتمل» عدد الصفوف المسلّمة التي لم تُنظف بعد، وليس تاريخ جميع المزامنات.
- دعم قراءة timestamps القديمة بالثواني والحالية بالميلي ثانية؛ لا تُعدّل الطوابع المخزنة.
- عتبات المرجع: FK>0 أو stuck>10 حرج؛ failed>20 أو العمر>10 دقائق خطأ؛ failed>5 أو pending>100 أو stuck>0 تحذير. وجود processing يمنع وصف الطابور بأنه فارغ/سليم تماماً.
- هذا **ليس فحص اتصال Worker/D1**. صفر FK يعني عدم رصد انتهاكات للقيود المعرفة فعلياً في SQLite، لا سلامة جميع الروابط المنطقية أو الخادم.
- فشل القراءة يُعرض كخطأ مع تحذير من قدم التقرير السابق، ولا يُستبدل بأصفار توحي بصحة زائفة.
- احتُفظ بهوية البطاقات والفواصل 16 من المرجع؛ لم تُدّع مطابقة screenshots. تحديث بالسحب غير مضاف؛ زر التحديث ومؤقت الظهور موجودان.

## الاختبارات والنتائج

- اختبارات عتبات التصنيف والحدود العددية.
- اختبار Room حقيقي: الحالات المحلية/المستوردة، أولوية acknowledgement، فشل primary، طوابع الثواني، العالق، توزيع الكيانات وعدم تغيير صفوف DB.
- فحص Bash النحوي ناجح، واختبار قارئ تقارير الجودة بملفات XML اصطناعية ناجح. أرقام هذه الملفات **ليست نتائج جودة المشروع**.
- التجميع واختبارات Android وعمليات المحاكي/الجودة يجب تأكيدها من GitHub Actions بعد الدفع؛ لا Java/SDK محليين، ولا قياسات هاتف أو نتائج جودة فعلية يُستنتج نجاحها من إعداد الملفات.
