# إلغاء المصروف والسحب بقيد عكسي

## النطاق والقرار

هذا التغيير يخص **expenses وsalary_withdrawals**. ليس محرك قيد مزدوج شاملاً، ولا يغيّر سياسة المدفوعات والديون ودورات الرواتب الأخرى. إقفال الفترة أدناه يحمي سجل المصروفات والسحوبات، وليس كل عناصر تقرير الدخل الشامل.

التطبيق لا يملك مرحلة اعتماد أو جدول مسودات للمصروفات. لذلك **الحفظ = اعتماد**، والحركة الموجودة معتمدة أيضًا. المسودة هي حقول شاشة الإدخال قبل الحفظ؛ إغلاقها لا ينشئ حركة. لا نعيد تصنيف الحركات القديمة كمسودات ولا نحذفها أو نخمن روابطها.

- لا تعديل ولا حذف مالي مباشر بعد الحفظ. التصحيح: إلغاء الأصل بقيد عكسي ثم تسجيل البديل عند الحاجة.
- تبقى الحركات القديمة (بما فيها علامات الحذف السابقة) كما هي. لا تعيد الترحيلات كتابة أموال الماضي.
- زر المصروف أصبح «إلغاء بقيد عكسي» مع سبب إلزامي (3–500 حرف).
- إلغاء القيد العكسي نفسه ممنوع. المبلغ الموجب الأصلي يُعكس كاملاً، وليس جزئيًا.

## المزامنة والذرية

1. يحفظ Android أمر Outbox واحدًا `operation=reverse` يحتوي UUID المصدر والسبب، وليس مبلغًا سالبًا يثق به الخادم. النقر المكرر يعيد نفس الطلب المحلي. يبقى الطلب وإيصاله محفوظين للتشخيص.
2. لا يُغيّر الطلب الرصيد محليًا قبل القبول. يظهر «إلغاء بانتظار المزامنة». أعطال الاتصال/الخادم العابرة لا تُسقط طلب الإلغاء بسبب سقف المحاولات.
3. يستخرج الخادم الأصل من D1 ويحسب المبلغ والتاريخ بنفسه. المنفّذ هو `ctx.userId` من جلسة Worker الموثقة، لا اسم يرسله العميل. إذا استُخدم حساب مزامنة مشترك، فالتدقيق ينسب العملية لذلك الحساب؛ لا يدّعي إثبات الموظف المحلي الفعلي.
4. إن كان السحب مرتبطًا بمصروف، تُوجَّه عملية عكس السحب إلى المصروف نفسه. يُنشأ مصروف سالب وسحب سالب مرتبط **بـ UUID المصروف العكسي**. يظل التقرير يخفي التمثيل المكرر فقط، لا أصلين مستقلين.
5. تُكتب جميع الأرجل وسجل `financial_events` وطوابع التعارض وتخصيص مؤشر المزامنة في **D1 batch واحدة**. فشل السحب يعيد المصروف والتدقيق والمؤشر إلى ما قبل العملية.
6. قيود uniqueness على مصدر التصحيح تمنع تكرار الأثر حتى عند اختلاف مفاتيح طلب جهازين أو ضياع الرد. إعادة الطلب تعيد الإيصال نفسه.
7. تشترك الأرجل في مؤشر واحد داخل المعاملة؛ آلية إكمال مجموعة المؤشر في pull تبقيها في الصفحة نفسها حتى مع `limit=1` (السحب الشامل المعتاد، دون فلتر كيان منفرد). مصدرها `financial-ledger` حتى لا يحجبها فلتر صدى جهاز الطلب.
8. يتضمن رد الدفع الأصل والتصحيح والأرجل المقترنة. يطبق Android الإيصال داخل معاملة Room واحدة قبل تأكيد وصول الأمر. عند فقد والد محلي أو فشل التخزين تعاد المحاولة، ولا يُعرض نصف إيصال. تبقى آلية pull الاعتيادية للنسخ الأخرى.

التصحيح في اليوم الفندقي الحالي **بتوقيت عدن UTC+3، وحدّ 14:01** من ساعة الخادم. لا يستخدم تاريخ الجهاز أو تاريخ الطلب القديم إذا تأخر وصوله. هذا يحافظ على الفترة المقفلة، ويغيّر الرصيد التراكمي بمقدار التصحيح. لا يعني أن الرصيد لا يتغير.

## الإقفال الإداري

يتطلب اتصالًا وصلاحية Worker `admin`. أُضيفت واجهة API، **ولم تُضف شاشة إقفال داخل التطبيق في هذا التغيير**.

- `GET /api/financial/policy` للمستخدم الموثّق: اليوم الفندقي الحالي، آخر يوم مقفل، ونطاق الجداول المحمية.
- `POST /api/admin/financial/close-period` بجسم JSON مثل:

```json
{"closed_through":"2026-09-30","reason":"تمت المطابقة بعد مزامنة جميع الأجهزة"}
```

يقفل جميع الأيام حتى التاريخ **شاملاً**. لا يمكن إقفال اليوم الحالي أو يوم مستقبلي أو إعادة فتح فترة. يُسجّل سبب الإقفال ومنفّذه.

تفرض triggers قاعدة D1 منع تحديث الحقول المالية أو حذفها أو استبدال UUID موجود. تمنع إدراج حركة في فترة مقفلة داخل معاملة الإدراج نفسها، بما فيها طريق إضافة المصاريف عبر AI. مسار الاستيراد SQL العام لا يقبل جدولَي المصروفات والسحوبات حتى لا يصبح ثغرة لإعادة كتابة التاريخ.

الإقفال يفشل إذا وُجد مصروف موظف حتى التاريخ المطلوب بلا سحب UUID متطابق (الموظف والمبلغ واليوم). الفحص داخل معاملة الإقفال لتجنب إقفال نصف عملية أثناء المزامنة. لا يستطيع الخادم معرفة الطلبات التي لم تغادر جهازًا مفصولًا: **مزامنة كل الأجهزة وفحص المرفوضات والمطابقة شرط تشغيلي قبل الإقفال**. أي إنشاء متأخر مؤرخ بفترة مقفلة يرفضه الخادم؛ لا يُعاد تأريخه أو ترحيله تلقائيًا. نظام الإنشاء المحلي الحالي ليس نظام اعتماد خادمي شاملًا؛ راجع الصف المحلي وOutbox المرفوض قبل اعتماد تقارير الجهاز.

## الحالات التي تفشل بأمان

- مصروف موظف بلا رابط سحب مؤكد، أو اختلاف المبلغ/اليوم/الموظف: لا تصحيح جزئي ولا تخمين. أعد المزامنة أو راجع البيانات.
- سحب تاريخي يحمل `exp_N` بلا `expense_uuid`: يحتاج مراجعة، لا يُعامل كمستقل.
- مصروف مرتبط بـ `cash_transaction_id` أو `cash_flow_uuid` تاريخي: يمتنع المسار الحالي عن عكسه؛ يلزم تصميم تصحيح مترابط لسجل الصندوق أيضًا.
- قيد عكسي أو أصل محذوف سابقًا أو مبلغ غير موجب: رفض دائم.
- خطأ دائم يظهر في حالة الطلب؛ لا يحذف الأصل ولا يغير الرصيد. الخطأ العابر يعاد تلقائيًا. معالجة طلب مرفوض بعد إصلاح بيانات تاريخية تحتاج مراجعة تشخيصية؛ لا يوجد زر لإعادة إرسال الطلب المرفوض في هذه النسخة.
- المدفوعات والديون والسياسات الخاصة بها خارج هذا التغيير. لا تصف هذا الإقفال بأنه تجميد لكامل تقرير الفندق.

## الترحيل والنشر — لا يُنفّذ تلقائيًا

- Room **73**: إضافة `reversal_of_uuid`, `reversal_reason`, `reversal_actor` إلى المصروف والسحب. مسارات 70→71→72→73، 71→72→73، 72→73. لا حذف أو تعديل للأموال أو Outbox، ولا destructive fallback.
- D1 **0015_financial_reversals.sql** بعد 0013 و0014؛ يضيف الأعمدة والفهارس وسجل التدقيق وقفل الفترة والحمايات. `schema.sql` يتضمن بنية التثبيت الجديد. ملف ALTER للترقية يُطبّق مرة واحدة بواسطة سجل الترحيلات، وليس بشكل متكرر.
- خذ نسخة احتياطية، اختبر نسخة staging، وراجع جميع الروابط القديمة والطلبات المعلقة قبل التفعيل.
- أوقف الكتابة خلال الترحيل، ثم طبّق D1 وانشر Worker المتوافق قبل إصدار Android. لا تُشغّل `db:init` على قاعدة موجودة بدل الترحيلات.
- حدّث جميع الأجهزة قبل السماح بالعمل المالي. العميل القديم قد يعرض تعديله المحلي رغم رفض الخادم؛ الحماية الخادمية لا تصلح واجهة عميل قديم. راجع/سوِّ طلبات update/delete المالية القديمة بدل إسقاطها بصمت، ثم أجرِ إعادة سحب كاملة ومطابقة. لا تمسح قاعدة الجهاز أو Outbox لتجاوز أخطاء الترقية.
- واجهة API الإدارية لا تتطلب نشرها أو استدعاءها أثناء تطوير هذا التغيير. **لم تُطبّق ترحيلات أو إقفالات على الإنتاج.**

## الاختبارات

Worker: عكس زوج المصروف والسحب، الإيصال وإعادة الطلب، تنافس جهازين، فشل السحب وإرجاع المعاملة والمؤشر، وصول الأرجل مع حد صفحة واحد وفلتر صدى، رفض تعديل/حذف الأجهزة القديمة والقيد المزور والاستيراد، بقاء مجاميع الفترة المقفلة، صلاحية المسؤول، حدود اليوم الفندقي، السحب المستقل، والترقية الفعلية من بنية قبل 0015.

Android: منع تعديل الأصل وحذفه، حفظ طلب واحد دون تغيير المال، rollback لإيصال ناقص الوالد، إعادة تطبيق الإيصال دون تكرار المبلغ، حفظ حقول التدقيق، ترحيل Room وحفظ المال وOutbox، وعدم احتساب تمثيل السحب العكسي مرتين في التقرير.
