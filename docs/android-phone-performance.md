# تحسين الأداء على الهاتف — الدفعة الأولى

## ما كشفته مراجعة الكود وما تغيّر

| الموضع | السبب المحتمل للعمل الزائد | التغيير |
|---|---|---|
| الرئيسية | مراقبان مستقلان للحجوزات: حالة الغرف وخريطة الانتقال، والثاني يبقى نشطًا طوال عمر ViewModel | مصدر مشترك يُراقَب عند وجود مستهلكين؛ اشتقاق الخريطة بدون collector دائم؛ الاحتفاظ بدلالات الأخطاء لكل مستهلك |
| الرئيسية | تحديثات المزامنة تُقرأ في الجذر وتعيد تنفيذ محتوى الشاشة | عزل اشتراك حالة المزامنة وعدّاد المعلّقات داخل مكوّن الرأس |
| الرئيسية | تحويل الحجوزات وتجهيز حالات الغرف على سياق جامع الواجهة | تشغيل التحويل والاشتقاق على Dispatchers.Default |
| قائمة الحجوزات | التجميع والفرز وتحليل التواريخ وتجهيز الصفوف ضمن viewModelScope/Main | نقل المراحل الحسابية إلى Default؛ نشر حالة الواجهة يبقى على Main |
| الرئيسية والحجوزات والإعدادات | collectAsState لا يتوقف لمجرد انتقال Activity للخلفية | collectAsStateWithLifecycle؛ مصادر الرئيسية WhileSubscribed تتوقف بعد مهلة 5 ثوانٍ |
| تنسيق التواريخ | SimpleDateFormat مشترك وغير آمن عند العمل المتوازي | حماية كل منسق مشترك بقفل قصير، دون تغيير الأنماط أو معادلات الأيام |
| حزمة الإصدار | ui-tooling ضمن implementation رغم كونه أداة تطوير | حصره في debugImplementation؛ مقدار تقليل الحجم غير مقاس |

المشاركة تحفظ نتيجة المصدر/الخطأ ثم توزعهما؛ لا تُحوّل أخطاء قاعدة البيانات إلى قائمة فارغة ناجحة. عند توقف جميع المستهلكين يُزال replay الخاص بالمصدر، وتُقرأ البيانات من جديد عند الرجوع. قيم StateFlow المعروضة قد تبقى حتى وصول التحديث كما في السابق.

## ما لم يتغير

- لا حذف للسجلات أو اقتصاص لقائمة الحجوزات بهدف إظهار سرعة مصطنعة.
- لا تغيير لمعادلات المبالغ، ترتيب الصفوف، اليوم الفندقي أو صلاحيات المستخدم.
- لا تعطيل للحفظ أو outbox أو الاسترداد بعد الانهيار أو المزامنة التلقائية.
- AutoSyncEngine يستخدم أصلًا Dispatchers.IO؛ لم يُعدّل توقيته في هذه الدفعة. دورة الأمان الساعية في Dashboard بقيت كذلك.
- قائمة الحجوزات تستخدم أصلًا LazyColumn؛ لا حاجة لاستبدالها باسم تحسين الأداء.
- ليست كل ViewModels متوقفة في الخلفية: pipeline قائمة الحجوزات الحالي ما زال launchIn(viewModelScope)، وإن توقف جمع الواجهة. تحسين lifecycle الشامل لباقي الشاشات عمل منفصل.
- لم يُنفّذ بعد paging من قاعدة البيانات أو Baseline Profile أو قياس إقلاع على جهاز. القراءة الكاملة للسجلات الكبيرة تبقى نقطة يجب قياسها.

## التحقق

- DashboardDataFlowsTest: مستهلكان يقابلهما اشتراك مصدر واحد، لا تشغيل قبل الاشتراك، توقف عند غياب المستهلكين، إعادة تحميل دون replay قديم، ووصول الخطأ إلى المستهلكين.
- HotelTimeFormattingConcurrencyTest: مقارنة نتائج المنسقات الأربعة تسلسليًا ثم عبر أربعة خيوط وتواريخ مختلفة.
- اختبارات الحسابات الحالية باقية؛ لم تُخفَّض معاييرها.
- تُشغّل اختبارات Android وبناء APK عبر GitHub Actions؛ لا توجد Java/Android SDK محلية في بيئة العمل الحالية.

## القياس المطلوب قبل الحكم على سرعة الهاتف

يُستخدم APK release الموقّع، لا debug أو release غير المصغّر. على جهاز اقتصادي وجهاز متوسط، ومع نفس البيانات قبل/بعد:

1. قياس cold start وwarm start عدة مرات، مع فصل وقت إظهار البيانات المحلية عن اكتمال المزامنة.
2. قياس frame times/jank أثناء تمرير الحجوزات وفتح الرئيسية مع بيانات اختبار كبيرة.
3. تسجيل الذاكرة وGC وزمن استعلامات قاعدة البيانات بواسطة Android Studio Profiler أو Perfetto.
4. تجربة العودة من الخلفية، انقطاع الشبكة، مزامنة كبيرة وتحديث غرفة أثناء عرض الرئيسية.
5. اختبار حدود 14:01 و22:00 و23:00 و05:00 والانتقال إلى شاشة الدفع بعد تحديث الحجز.

لا تتضمن هذه الدفعة نسبة تسريع أو زمن إقلاع مثبتًا؛ الاختبارات الوظيفية ليست benchmark، والتحسينات البرمجية لا تكفي وحدها لضمان سلاسة كل هاتف.
