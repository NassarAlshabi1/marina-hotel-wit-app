# Macrobenchmark وبوابة المقاييس — تنفيذ مصحح لمقترح ttyy.txt

## النطاق الفعلي

هذا التنفيذ لا يعلن جاهزية الإصدار ولا يقيس سرعة هاتف فعلي. ينفذ إقلاعًا باردًا ودافئًا إلى **شاشة الدخول الفعلية** على محاكي مؤقت معزول عن الشبكة، ويقرأ النتائج الحقيقية. لا توجد تسجيلات دخول أو عمليات مالية أو تمريرات شكلية تُحسب كاختبار للحجوزات.

- التطبيق: `com.a.a`، compile/target SDK 35، min SDK 26، AGP 8.6.1، Kotlin 1.9.23.
- Gradle بقي Groovy، ولم تُستبدل ملفات البناء بملفات Kotlin DSL.
- وحدة `com.android.test` باسم `macrobenchmark`، باعتمادات `implementation` ومصادر `src/main`، وvariant مطابق باسم `benchmark`.
- AndroidX Macrobenchmark **1.2.4** وUI Automator **2.3.0** وRunner **1.5.2** مثبتة لهذه السلسلة من أدوات البناء؛ ليست ادعاء بأنها أحدث الإصدارات.
- التطبيق المقاس غير قابل للتصحيح، مصغّر بـR8، وموقّع بمفتاح debug المحلي. لا تستخدم APK الاختبار كنسخة إصدار.
- `<profileable>` موجود في `src/benchmark` فقط؛ لم تُغيّر قابلية تتبع نسخة release.
- تفعيل الوحدة اختياري عبر `-PenableMacrobenchmark`، فلا تصبح مكتبات القياس شرطًا لبناء التطبيق العادي.

## ما أُصلح مقارنة بالمقترح

1. لم يعد القارئ يجمع كل الأرقام من ملفات JSON عشوائية.
2. أسماء الاختبارات والمقاييس ووحداتها وعدد التكرارات مطلوبة من سياسة صريحة. غياب أي نتيجة مطلوبة خطأ، وليس صفرًا أو نجاحًا.
3. يُحسب median وP50/P90/P95/P99 من `runs`، لا من حقول الملخص التي قد تكون غير متسقة.
4. عينات الإطارات تؤخذ من `sampledMetrics` فقط؛ لا تُخلط بزمن الإقلاع أو RAM أو timestamps.
5. `frameOverrunMs` يمكن أن يكون سالبًا، بخلاف مدة CPU للإطار؛ لا يُعامَلان على أنهما المقياس نفسه.
6. تُرفض القيم غير المحدودة وNaN وbooleans والعينات الفارغة والتكرارات الناقصة والنتائج المكررة والسياقات المختلطة ومفاتيح JSON المكررة.
7. حدود التحذير والفشل تُطبّق فعلًا عند طلب enforcement. القيم التي تساوي الحد تُصنَّف ضمن التحذير/الفشل، لا أقل منه.
8. مسارات المخرجات مطابقة لإعادة توجيه المشروع إلى `mobile/build`.
9. فشل جودة الكود القديمة لا يمنع جمع الأدلة التشخيصية؛ المساران مستقلان، ولا يتحول فشل Detekt إلى نجاح.
10. فحص crash/ANR مقيّد بحزمة التطبيق، ولا ينسب انهيار عملية نظام أخرى إلى الفندق.

## الاختبارات والأمان

`EntryStartupBenchmark` ينفذ 8 تكرارات باردة و8 دافئة، مع `CompilationMode.Full()` في الحالتين. ينتظر `marina_login_screen` المنشور بواسطة Compose `testTagsAsResourceId`، ليثبت أن شاشة الدخول ظهرت، لا مجرد نافذة الإقلاع.

- القياس هو `timeToInitialDisplayMs`، وليس زمن اكتمال كل عمليات الخلفية أو TTFD.
- الإقلاع الدافئ يهيئ التطبيق قبل الجزء المقاس ثم يعود إلى الشاشة الرئيسية.
- لا توجد بيانات غرف/حجوزات اصطناعية في هذه الدفعة، ولا قياس تمرير أو P95/P99 فعلي للإطارات. دعم القارئ لهذه المقاييس واختبار معادلته لا يُعد دليل قياسها في التطبيق.

سكربت التشغيل يرفض الأجهزة غير الافتراضية، يثبت APKs مرة واحدة، يمسح بيانات التطبيق على المحاكي المؤقت، ثم يحظر IPv4 وIPv6 لكلا UID التطبيق والاختبار ويتحقق من القواعد قبل تشغيل instrumentation. لا يُسمح لفشل العزل بالمرور. الاختبار نفسه يتطلب علامة تحقق السكربت ويرفض الهاتف الفعلي.

**لا تشغّل السكربت على محاكي يحتوي بيانات تريد الاحتفاظ بها**؛ هو مخصص لبيئة CI جديدة، ويمسح بيانات `com.a.a`. توقيع APK التجريبي لا يطابق بالضرورة توقيع النسخة المثبتة عند المستخدم.

المحاكي API 34 / Pixel 2 / نواتان / RAM مطلوبة 1024 MiB. حجم الذاكرة الفعلي محفوظ في الأدلة؛ هذا ليس محاكاة دقيقة لهاتف بذاكرة 1GB. استثناء `EMULATOR` مفعّل لهذا الفحص التشخيصي فقط، ولا توجد استثناءات عامة لـDEBUGGABLE أو أخطاء الإعداد الأخرى.

## بوابة المقاييس

السياسة الحالية: `config/benchmark/entry-startup.json`.

| المقياس | إحصائية القرار | تحذير | فشل |
|---|---|---:|---:|
| الإقلاع البارد TTID | median من 8 تكرارات على الأقل | 2500ms | 4000ms |
| الإقلاع الدافئ TTID | median من 8 تكرارات على الأقل | 1500ms | 2500ms |

هذه حدود أولية غير مُعايرة؛ يلزم ضبطها بنتائج متكررة على جهاز معتمد. ليست حدود Android الرسمية ولا شهادة أداء.

### diagnostic

يستخدمه CI الحالي. يعود برمز 0 إذا كانت الأدلة صحيحة ومكتملة، حتى لو تجاوزت حدود الزمن، لكن الناتج يحمل دائمًا:

```json
{"status":"DIAGNOSTIC_ONLY","releaseEligible":false}
```

تظل `thresholdVerdict` لكل مقياس وللمجموعة ظاهرة: PASS أو WARNING أو FAIL. نجاح مهمة التشخيص يعني نجاح جمع الأدلة والتحقق منها فقط.

### enforce

متاح في القارئ لنتائج موثوقة من جهاز فعلي مُعدّ مستقلًا. يتطلب بصمة build معتمدة مطابقة، ويرفض مؤشرات المحاكي المعروفة. يعيد 1 لتجاوز حد الفشل، و2 للأدلة/السياسة غير الصالحة، و0 للنجاح أو التحذير. `releaseEligible` يبقى false لأن هذا فحص مقاييس فقط، وليس تجميعًا لاختبارات الوظائف والجودة والإصدار.

**لم تُجهز هذه الوحدة لتشغيل هاتف فعلي بعد**؛ الحارس يرفضه عمدًا حتى تتوفر بيئة اختبار محلية وبيانات اصطناعية آمنة. وجود خيار `enforce` ليس ادعاء بوجود نتائج جهاز فعلي.

## التشغيل

اختبارات القارئ محليًا:

```bash
python3 -m unittest discover -s tests/benchmark -v
```

بناء APKs الاختبار:

```bash
cd mobile/android
./gradlew -PenableMacrobenchmark :app:assembleBenchmark :macrobenchmark:assembleBenchmark
```

التشغيل المعزول يتم عبر `.github/workflows/android-macrobenchmark.yml`. أوامر ADB لها مهلة 90 ثانية، وinstrumentation له مهلة 10 دقائق، وخطوة المحاكي كلها 20 دقيقة. تُحفظ مراحل التنفيذ في `phases.txt`؛ انتهاء المهلة فشل في جمع الأدلة، وليس رقم أداء أو نجاحًا. لا تنفذ أمر connected-test يدويًا ثم تفترض أن الشبكة معزولة؛ السكربت يثبت ويفحص العزل قبل تشغيل الاختبارات المثبتة مباشرة.

قراءة النتائج التشخيصية، من جذر المستودع:

```bash
python3 .github/scripts/performance-gate.py \
  --results path/to/com.a.a.macrobenchmark-benchmarkData.json \
  --policy config/benchmark/entry-startup.json \
  --mode diagnostic --output performance-summary.json
```

## الأدلة والمتابعة

الـartifact `offline-entry-macrobenchmark` يحفظ APKs وmapping ونتائج JSON وPerfetto traces وسجل instrumentation وقواعد العزل ولقطات ذاكرة/رسم موجهة لحزمة التطبيق. هذه اللقطات ليست بحد ذاتها قياسات CPU/GC معيارية أو بوابات لها.

النطاق المتبقي: تدفقات Dashboard/Bookings/Payments/Expenses بحساب وبيانات اصطناعية معزولة، تحقق من تنفيذ التمرير الفعلي، سياسة عينات مناسبة لـP95/P99، تجهيز جهاز فعلي مضبوط، ثم ربط نتائج معتمدة بسياسة إصدار صريحة. لم تُضف موافقة نشر تلقائية أو حماية فرع باسم Release Gate.
